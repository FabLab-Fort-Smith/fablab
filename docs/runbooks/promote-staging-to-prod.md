# Runbook: Promote staging to production

> **Production is Coolify.** Since **2026-08-03**, `fablabfortsmith.org` (+ `www`) is served by the
> **`the-lab-production`** Coolify application on the VPS, deployed from **`main`**. The Vercel
> project has been **deleted** — it is no longer a rollback path (see §Rollback).
>
> Two environments, two apps, two secret files — never mixed:
>
> | | staging | production |
> |---|---|---|
> | app | `the-lab-staging` | `the-lab-production` |
> | branch | `dev` | `main` |
> | URL | `staging.fablabfortsmith.org` | `fablabfortsmith.org` + `www` |
> | secrets | `../.env` | `../.env.production` |
> | Square | sandbox | **production** (live since 2026-09-04, #180-era cutover) |
>
> Rules: `@rules/workflow-release.md`, `@rules/topic-config-environments.md`,
> `@rules/workflow-gated-actions.md`.

> ## 🔒 Promotion gate (MANDATORY — read first)
> **Promotion chain: local `dev` → GitHub → **staging** → production. Production is deployed
> DELIBERATELY, never automatically, and NEVER without explicit human approval.**
>
> - **Auto-deploy on push to `main` is DISABLED** for `the-lab-production` (toggled off 2026-09-06,
>   Coolify UI — the flag is not settable via the API). So a merge to `main` **no longer deploys
>   prod**. This runbook's `reconcile.sh … --confirm-production --deploy` (or the Coolify **Deploy**
>   button) is now the *only* path to prod — not a break-glass alternative.
> - **Never merge to `main` as a way to ship prod, and never run the deploy step, without explicit
>   per-action owner approval.** `main` == prod: treat any prod deploy as gated
>   (`@rules/workflow-gated-actions.md`).
> - **Validate on staging first.** `staging.fablabfortsmith.org` (`dev`) must run the change and be
>   verified before you promote. CI green ≠ validated.
> - If auto-deploy is ever re-enabled, this gate is defeated — keep it OFF.
>
> _Why this exists: on 2026-09-06 a `dev→main` release PR (#190, v1.0.0) auto-deployed to prod on
> merge, bypassing staging and approval, because `main` auto-deploy was on. Kept v1.0.0 (it was
> tested + SEC-reviewed + staging-validated; a revert would have reintroduced patched CVEs), disabled
> auto-deploy, and wrote this gate. See `prod-promotion-gate` (agent memory)._

## When to use
- A change is merged to `main` and should go live on the apex.
- Production app config or env changed and needs re-applying (idempotent).
- You are reading the historical record of the Vercel→Coolify cutover (§Cutover record).

## Prerequisites & access
- `../.env` holds `COOLIFY_URL` + `COOLIFY_TOKEN` (platform creds; see `coolify-token-rotation.md`).
- `../.env.production` exists and holds the **production** app secrets. It is git-ignored and
  **must not** be generated by `make secrets` — see the ENCRYPTION_KEY warning below.
- `jq`, `curl`. Tailnet up (the Coolify API is tailnet-only, ADR 0012).

> **⚠ ENCRYPTION_KEY — data-loss risk.** `.env.production`'s `ENCRYPTION_KEY` is the **original
> production key carried over from Vercel**. Member emails are encrypted at rest with it. If it is
> ever regenerated, **every stored email becomes undecryptable** — email login breaks and member
> outreach cannot resolve recipients. Never let `gen-secrets.sh`/`make secrets` touch this file; the
> vault copy is `PROD_ENCRYPTION_KEY` in the Infrastructure collection.

## Steps — routine promotion
> **Pre-release step (#107):** refresh staging from production first, so you are testing against
> production-shaped data rather than drift:
> ```bash
> cd lab-stack && bash scripts/refresh-staging-from-production.sh --yes
> ```
> It anonymizes and **fails closed** — see `refresh-staging-from-production.md`.


1. **Confirm the change is on `main` and green.** CI must be green on the merge commit
   (`@rules/workflow-cicd.md`). Note: merging to `main` **does not deploy prod** (auto-deploy is off);
   promotion is the explicit deploy in step 4.
2. **Confirm it has soaked + was validated on staging.** `staging.fablabfortsmith.org` (`dev`) must be
   running the change and verified — functionally, not just green CI — before promoting.
   **➜ Get explicit owner approval to deploy to production now** (gated action —
   `@rules/workflow-gated-actions.md`). Do not proceed to step 4 without it.
3. **Plan the production apply (no writes):**
   ```bash
   cd lab-stack && bash coolify/reconcile.sh --env production --dry-run
   ```
   Check the target line reads `the-lab-production`, branch `main`, domains apex + `www`, and
   secrets from `../.env.production`. Review the `EMPTY` list — those keys will not be set.
4. **Apply + deploy** (production writes are gated, hence the extra flag):
   ```bash
   bash coolify/reconcile.sh --env production --confirm-production --deploy
   ```
5. **Watch the rollout.** Poll the deployment until `finished` and the app reports
   `running:healthy`, then verify (below). This deliberate, approval-gated deploy is the **only** path
   to prod — auto-deploy on `main` is disabled (see the Promotion gate). The Coolify **Deploy** button
   on `the-lab-production` is the equivalent manual trigger.

## Verification
6. **Public surface:** apex and `www` return `200`; `/auth/signin` `200`; `/dashboard` `307`
   (deny-by-default); `/auth/forgot-password` `200` (recovery must work while signed out **and** in).
   ```bash
   for u in https://fablabfortsmith.org https://www.fablabfortsmith.org \
            https://fablabfortsmith.org/auth/signin https://fablabfortsmith.org/dashboard; do
     printf '%s -> ' "$u"; curl -sS -o /dev/null -w '%{http_code}\n' "$u"
   done
   ```
7. **It is our app, not a stale edge:** response carries `x-powered-by: Next.js` and our
   `content-security-policy-report-only` header, and **no** `x-vercel-*` header.
8. **Guards live:** `GET /api/v1/users/auth-methods` → `401`;
   `POST /api/v1/admin/google-retirement-notice` → `401`.
9. **Sign in** and confirm you land on `/dashboard/<your userID>` — not `/dashboard/undefined`
   (The-Lab #186).

## Rollback / abort
> **There is no DNS-revert rollback any more.** The original plan kept Vercel warm and reverted DNS;
> the Vercel project was deleted at cutover, so that path is gone. Reverting the apex A record now
> just returns `404`.

10. **Application-level rollback:** redeploy the previous known-good deployment from Coolify —
    `redeploy-rollback.md`. This is the primary and, for app regressions, sufficient path.
11. **Config/env rollback:** `.env.production` is the source of truth; restore the previous value
    (vault: the `PROD_*` fields) and re-run step 4.
12. **Database:** production uses the **external MongoDB carried over from Vercel** (db `FabLab`),
    not the VPS instance — so an app rollback does **not** roll back data. Schema-affecting changes
    must be backward-compatible (`@rules/topic-database.md`, expand/contract).
13. **Total loss of the VPS** is the real risk now (single point of failure, no warm standby):
    rebuild via `rebuild-coolify-from-code.md` + `bootstrap-vps.md`, then re-apply step 4.

## Cutover record — Vercel → Coolify, 2026-08-03

What was actually done, in order:

14. **Vercel project deleted** by the owner (out of band). Apex served `404`
    (`x-vercel-error: DEPLOYMENT_NOT_FOUND`) until the cutover — i.e. there was **no live service to
    protect**, which is why the original parallel-run/rollback guardrails no longer applied.
15. **`reconcile.sh` taught about production** (`--env`, per-env secret file, `--confirm-production`)
    — PR #87, closing #85. Before this, production was pure click-ops.
16. **`.env.production` assembled**: the **existing** prod `MONGODB_URI` + `ENCRYPTION_KEY` (verified
    by decrypting live records), fresh session secrets, apex URLs, `NEXT_PUBLIC_APP_ENV=production`,
    Square **sandbox**, PurelyMail mailer, and a **dedicated production Turnstile widget**
    (`fablab-production`, apex + `www`; secret validated against Cloudflare `siteverify`).
17. **Applied**: 31 env vars synced, domains set to apex + `www`, deploy triggered → `finished`,
    app `running:healthy`.
18. **DNS cut over** in Cloudflare (records kept **proxied**): apex `A 76.76.21.21` (Vercel) →
    `A 107.173.52.204` (VPS); `www CNAME cname.vercel-dns.com` → `CNAME fablabfortsmith.org`.
    Mail records (MX, SPF, ownership TXT) were **not touched**.
19. **Verified**: apex/`www` `200` from our app, `/dashboard` `307`, both new APIs `401`, TLS valid.
20. **Secrets vaulted** as `PROD_*` fields (`The-Lab PRODUCTION app secrets (Coolify)`).

### Accepted risks recorded at cutover
- **Google sign-in is not configured on production.** `GOOGLE_CLIENT_ID`/`SECRET` are unset, so the
  **12 google-only members cannot sign in** and must use forgot-password. Accepted deliberately; the
  retirement notice email is the only channel that reaches them (the in-app nudge requires a session
  they cannot obtain). See `lab-site/the-lab/docs/analysis/google-oauth-removal-impact.md`.
- **No Vercel rollback** (above).
- **Production uses the external MongoDB, not the VPS instance** — a deviation from ADR 0010,
  accepted to avoid a data-migration window. Follow-up tracked to migrate it.
- **Unset on production:** `S3_*` (uploads/images broken), `GEMINI_API_KEY` (AI features off),
  `ADMIN_EMAIL` (admin notification mail has no recipient), `SQUARE_SDK_VERSION` (default).
- **Square remains sandbox** — payments are not live; flipping to production keys requires the
  PCI/SAQ-A re-check (`@rules/std-pci.md`).
- **Backups:** the VPS MongoDB is backed up and restore-drilled, but production data now lives in
  the **external** DB — its backup/restore posture is the provider's and is **not** covered by
  `backup-restore.md`. Verify it separately.

## Escalation
- Apex returns `503`: Traefik has no healthy backend — check the deployment status and container
  health in Coolify; a build failure leaves the previous container serving.
- Apex returns `404` with `x-vercel-*` headers: DNS is still pointing at Vercel — re-check the
  Cloudflare records from step 18.
- Coolify API `401`: the token is dead → `coolify-token-rotation.md`.
